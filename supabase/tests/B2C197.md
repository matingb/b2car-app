# B2C-197 database verification

Not executed/applied: task explicitly forbids DB reset or applying migration at this stage.
Run b2c197_precios_iva.sql with ON_ERROR_STOP in an isolated seeded database after migration.
The script is transactional and rolls back. It covers defaults, untouched legacy totals,
permission denial, missing rate, services/hours, latest form, input preservation, round-trip,
subsequent edits retaining rate, direct total override, partial/full collections, fiscal
states, pending budgets, tenant helper denial and commercial rounding.

## API contracts

- Atomic UPDATE of precios_incluyen_iva and tasa_iva (decimal fraction, e.g. .21).
  Only send tasa_iva on an **effective mode change**; same mode with a changed env rate
  must NOT overwrite the existing snapshot. A rate-only change is rejected.
- New/default/historical rows are true with NULL rate. NULL identifies legacy calculations;
  neither migration nor same-value/general edits repair historical money/form discrepancies.
- After first mode change a non-NULL rate is retained even when returning to included mode.
  These intentionally reinterpreted rows use canonical services + assignments + pending
  budget + latest form charge. Form metadata and employee/purchase costs are not taxed.
- Final per net line = round(input subtotal,2) + round(round(input subtotal,2)*rate,2).
  SQL and TS must use the same rule. Included legacy arithmetic stays unchanged.
- rpc_facturacion_preparar_documento FACTURA header must echo precios_incluyen_iva and
  tasa_iva from canonical loading for rows with snapshots. Total must match precio_final.
  Legacy included header remains compatible; notes do not compare to the full arreglo total.
- SQLSTATE 42501 permission/tenant, 22023 missing/invalid/rate-only mutation,
  55000 collected, 55001 protected fiscal state, 40001 stale fiscal preparation.

## Upgrade proof (separate pre-feature database)

Before applying ONLY the new migration: save complete arreglos row JSON (including
updated_at), line/operation/payment/form and fiscal snapshot JSON keyed by ID. After:
assert all old rows precios_incluyen_iva=true and tasa_iva IS NULL, and JSON equality
of every prior column/table. No UPDATE statement/backfill trigger is used by migration.
No reset between baseline and upgrade; empty reset alone cannot prove preservation.

## Concurrency QA (two real connections; not yet executed)

1. T1 BEGIN; SELECT arreglo FOR UPDATE; collect through existing collection RPC;
   T2 attempts toggle and waits. Commit T1 => T2 rejects 55000. Reverse order =>
   collection waits, then reads the new gross balance. Repeat partial/full and rollback.
2. T1 fiscal preparation RPC locks arreglo before factura, persists ENVIANDO; hold txn.
   T2 toggle waits then rejects 55001. Reverse => preparation rejects stale echoed
   mode/rate/total with 40001. Repeat INCIERTA and zero-rate equal-total toggles.
3. Two source line edits and toggle: source protection trigger takes the same row lock;
   recalculation also locks before loading inputs. Verify final equals canonical recompute.
   Deadlock/serialization victims must rollback/retry the entire operation, never one step.
4. Real authenticated PostgREST session without precios:edit must fail direct UPDATE;
   different tenant must see/update zero rows through unchanged RLS. SQL fixture tests
   trigger JWT enforcement but is NOT a replacement for real RLS role tests.

## Limitations / deliberate boundaries

- Postgres cannot authenticate the Node process environment value itself: authorized
  direct DB clients can provide a different valid commercial snapshot on a mode change.
  Backend must exclusively source the value from IVA_RATE/IVA_PERCENT, never client input.
- Existing service_role bypass is retained; direct privileged mutations are trusted.
- Lock guarantee for fiscal preparation is through the existing preparation RPC. Privileged
  raw INSERT/UPDATE of fiscal documents outside that RPC is not a validated preparation path.
- Arbitrary reassignment of source lines/operations between arreglos is legacy behavior;
  this feature does not redesign ownership-changing mutations or multi-parent operations.
- Canonical form is newest created_at, tie broken by ID; UI should use same tie ordering.
- Toggle intentionally canonicalizes a historical form discrepancy, but migration/general
  saves do not. Historical category breakdowns retain their existing omissions.
- Dashboard sum_ingresos remains a services-only metric (existing contract); category and
  employee breakdowns add the latest form only for reinterpreted snapshot rows.
- Pending budget activation and materialized repuestos/stock need existing integration
  suite plus the two-connection tests above before merge. No execution claimed here.
